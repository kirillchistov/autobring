# План реализации: AutoBridge

Отражает решения, принятые по итогам обсуждения. Дополняет `project-concept.md` и
`course-curriculum.md` — при расхождении в деталях этот документ приоритетнее (он более свежий).

## 0. Итоговые архитектурные решения

| Область | Решение | Обоснование |
|---|---|---|
| Рендеринг | **Next.js (App Router)** | SSR/streaming, файловый роутинг, Metadata API для SEO — то, чего React 19 сам по себе не даёт (см. пояснение ниже) |
| Backend | **Node/Express + PostgreSQL**, тонкий, вне глубокого разбора в курсе | Реальный продукт без превращения курса в backend-курс |
| Auth | **Собственная реализация**: bcrypt + JWT (access/refresh), httpOnly cookies | Реально, но без внешних провайдеров/зависимостей |
| Данные | Синтетический датасет 100–300 карточек, сгенерированные тексты и изображения (заглушки/стоки/SVG) | Без нарушения авторских прав конкурентов |
| Калькулятор пошлин | Реальные формулы РФ (актуальные на момент разработки), с дисклеймером «не юридическая/финансовая консультация», ставки — в вынесенном конфиге | Полезно и для курса, и для вас лично; проще обновлять при изменении ставок |
| Репозиторий | **Монорепо** (`apps/web`, `apps/api`, `packages/shared-types`) | Общие типы между фронтом и бэком, единая история |
| Деплой | **Vercel** — `apps/web` (Next.js); **Render/Railway** — `apps/api` + managed Postgres | Vercel не подходит для постоянно живущего Express+Postgres процесса так же хорошо, как для Next.js |
| Дизайн | shadcn/ui как база + осознанный «фирменный» слой (палитра, типографика, иллюстративные акценты) | Быстро, но не «шаблонно-ИИшно» |
| Темп | Компрессия учебной программы ~25% (слияние близких по теме модулей) | Более интенсивный спринт |

### Пояснение по React 19 vs Next.js
React 19 добавляет примитивы (Server Components, Actions, `use()`, потоковый рендерер),
но не даёт: файловый роутинг, HTTP-оркестрацию стриминга по маршрутам, конвенции загрузки
данных на уровне роута, оптимизацию изображений/шрифтов, Metadata API. Это работа фреймворка
(Next.js, Remix, React Router v7, TanStack Start). Поэтому Next.js остаётся оправданным выбором
для SEO/SSR-целей.

## 1. Структура репозитория

```
autobridge/
  apps/
    web/                  # Next.js App Router
      app/
        (marketing)/      # главная, блог — публичные, SEO-важные страницы
        catalog/
        cars/[id]/
        compare/
        account/          # защищённые маршруты
        api/               # route handlers, если что-то удобнее держать на фронте (напр. BFF-прокси)
      components/
      features/            # catalog, calculator, comparison, deal-timeline, auth...
      lib/
      hooks/
    api/                   # Express-приложение
      src/
        modules/           # cars, deals, users, auth, calculator-rates
        db/                # миграции, seed (Prisma рекомендуется)
        middleware/
  packages/
    shared-types/          # общие TS-типы Car, Deal, User, CalculatorInput/Output
    calculator-rates/      # конфиг ставок пошлины/утильсбора + версия/дата актуальности
  turbo.json / pnpm-workspace.yaml
```

Рекомендация: **pnpm workspaces + Turborepo** для монорепо (быстрые кэшируемые сборки,
общие типы без публикации отдельного npm-пакета). **Prisma** как ORM для Postgres —
даёт типобезопасность на бэке, которая естественно продолжается в `shared-types`.

## 2. Auth — дизайн потока

1. Регистрация/логин на `apps/api` (`/auth/register`, `/auth/login`) — bcrypt-хэш пароля.
2. При успехе — access-JWT (короткий TTL, 15 мин) в теле ответа, refresh-JWT — httpOnly
   Secure cookie (7–30 дней).
3. `apps/web` держит access-токен в памяти (не localStorage — риск XSS), обновляет через
   `/auth/refresh` при 401.
4. Next.js middleware проверяет наличие валидной сессии для `account/*` маршрутов,
   редиректит на логин при отсутствии.
5. Роли: `buyer` (по умолчанию), `admin` — на будущее для Фазы 3/Модуля 14 (админка).

Это даёт реальный, но некомплексный auth — достаточно глубоко для темы «защищённые маршруты
и работа с токенами в React/Next», не переусложняя внешними провайдерами.

## 3. Калькулятор пошлин — как поддерживать актуальность

- Все ставки (возрастные категории, объём двигателя, коэффициенты, утильсбор) — в
  `packages/calculator-rates` как версионируемый JSON/TS-конфиг с полем `effective_from`.
- Формула расчёта — чистая функция в `shared-types`/отдельном пакете, покрытая unit-тестами
  (хороший материал для Модуля тестирования — тестируем именно бизнес-логику, а не UI).
- На UI — плашка «Расчёт ориентировочный, по ставкам на [дата]. Актуальные ставки уточняйте
  у брокера/на сайте ФТС» — обязательный дисклеймер, без него калькулятор не публикуется.
- Отдельная заметка себе: поскольку ставки реальны, стоит выделить время вне курса, чтобы
  свериться с действующими формулами ФТС на момент запуска Модуля 3 — я могу помочь
  сформулировать формулу расчёта, когда дойдём до этого модуля, и свериться через веб-поиск
  на актуальность на тот момент (данные могут отличаться от того, что мы заложим сейчас).

## 4. Данные и изображения

- **Тексты/характеристики:** сгенерированные карточки (марка/модель/год/пробег/объём/оценка/
  цена) на основе публичных нейтральных фактов о моделях (Toyota Sienta, Honda Freed и т.д.
  — сами по себе не копирайт), без копирования маркетинговых текстов конкурентов.
- **Изображения:** три уровня на выбор по мере разработки —
  1. **SVG-силуэты авто** (просто, быстро, стилистически можно оформить в фирменном духе — низкий риск, максимальная скорость)
  2. Небольшой набор **royalty-free стоковых фото** (более «настоящий» вид витрины)
  3. Сгенерированные изображения через image-gen инструмент (когда дойдём до соответствующего модуля/потребности)
- Рекомендация на старте: **SVG-силуэты** — не блокируют разработку, не создают лицензионных
  вопросов, и хорошо сочетаются с «фирменным» дизайн-слоем (п.5).

## 5. Дизайн-система

- База: shadcn/ui + Tailwind (быстро, безопасно, доступно из коробки).
- Фирменный слой (чтобы не выглядело шаблонно):
  - Кастомная цветовая палитра, отличная от дефолтного shadcn slate/zinc (например,
    тёплая нейтральная база + один акцентный цвет, отсылающий к теме — не «дефолтный AI-фиолетовый»)
  - Осознанная пара шрифтов (не Inter+Inter) — один для заголовков с характером, один
    нейтральный для текста
  - Иллюстративные акценты (SVG-силуэты машин, простая линейная графика для шагов
    таймлайна сделки) вместо стоковых иконок везде
  - Асимметричные/неочевидные композиции хотя бы на 2–3 ключевых экранах (главная,
    карточка авто), а не «карточки в сетке 3×N» по умолчанию
- Это фиксируется отдельным чек-листом при старте Модуля 0/1 (дизайн-токены до вёрстки компонентов).

## 6. Компрессия учебной программы (~25%)

Исходные 15 модулей (0–14) → **11 модулей**. Слияния:

| Новый модуль | Из старых модулей | Комментарий |
|---|---|---|
| 0. Фундамент + компоненты | 0 + 1 | Каркас и compound-компоненты — логично идут вместе |
| 1. Состояние: Context/useReducer → Zustand (+TS) | 2 | Акцент на TS-типизацию стора — ваш заявленный пробел |
| 2. Формы: RHF + Zod | 3 | Без изменений, отдельный модуль — форм много и они сложные |
| 3. Server state: TanStack Query (+TS generics) | 4 | Акцент на типизацию query/mutation — ваш пробел |
| 4. Производительность + Concurrent React | 5 + 6 | Виртуализация и Suspense/useTransition — смежные темы оптимизации UI |
| 5. Real-time (WebSocket/SSE) | 7 | Без изменений — самостоятельная сложная тема |
| 6. Кастомные хуки — рефакторинг | 8 | Без изменений, но короче по времени (меньше «новой» теории) |
| 7. Auth + защищённые маршруты + таймлайн сделки | 9 | Без изменений |
| 8. Компаратор + drag & drop | 10 | Без изменений |
| 9. Тестирование | 11 | Без изменений |
| 10. Мультистрана + перформанс-аудит + деплой | 12 + 13 + 14 | Финальный «продакшн» модуль — обобщение источников данных, аудит, деплой и опциональная админка вместе |

Итог: **11 модулей**, сохранены все сложные темы, за счёт слияния смежных и сокращения
повторной теории (учитывая ваш текущий уровень) экономим время без потери глубины именно
там, где вы отметили пробелы (TS + Redux/Query-паттерны, concurrent features, virtualization, real-time).

## 7. Порядок работ (спринты)

Каждый спринт = 1 сжатый модуль. Оценка длительности ориентировочная, подстраивается под
ваш темп.

**Спринт 0 — Инфраструктура (перед Модулем 0)**
- Инициализация монорепо (pnpm + Turborepo), `apps/web` (Next.js), `apps/api` (Express + Prisma)
- Postgres (локально в Docker для разработки), базовая схема (`Car`, `User`, `Deal`)
- `packages/shared-types`, `packages/calculator-rates` (заготовка)
- Генерация синтетического датасета (100–300 карточек) — сделаю как отдельный шаг
- Дизайн-токены: палитра, типографика, база shadcn с кастомной темой
- Деплой-пайплайн: Vercel (web) + Render/Railway (api) — «hello world» до старта основной разработки, чтобы CI/CD не мешал на финише

**Спринты 1–10 — по одному на каждый сжатый модуль (1–10 из таблицы выше)**
Каждый спринт заканчивается работающим приростом функциональности (чекпоинты из
`course-curriculum.md`, актуализированные под Next.js/реальный backend).

**Спринт 11 — Продакшн-модуль (бывш. 12+13+14)**
Мультистрана, аудит производительности, финальный деплой, опциональная админка.
